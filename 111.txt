请检查当前本地项目中的 LWC、Apex、Salesforce Metadata、MuleSoft Flow、API定义和部署配置，根据现有代码给出针对性的异步架构改造方案。

一、当前问题

当前调用链大致为：

LWC
→ Apex
→ MuleSoft API
→ 外部AI服务
→ MuleSoft返回
→ Apex返回
→ LWC显示结果

由于AI处理时间较长，Salesforce调用MuleSoft时会超过120秒限制。多人同时使用时，还可能导致MuleSoft同时维持大量长时间AI请求。

二、目标架构

必须使用：

1. Salesforce Job Object保存任务状态。
2. Salesforce Platform Event进行异步通知。
3. MuleSoft直接将最终业务数据保存到现有Salesforce Object。
4. 不新建结果Object，不调整已经完成的数据Object设计。
5. LWC不能一直等待MuleSoft HTTP响应。
6. 用户切换页面、关闭页面或重新打开页面后，必须能够恢复并显示原任务状态。
7. Job Object是任务状态的唯一可信来源，事件只负责通知。
8. 除非现有负载确实需要，否则不要引入Anypoint MQ。

目标调用流程应为：

LWC提交申请
→ Apex创建Job记录
→ Apex在事务提交后发布“任务申请事件”
→ Apex立即向LWC返回Job Id
→ MuleSoft订阅申请事件
→ MuleSoft调用AI服务
→ MuleSoft将最终数据直接保存到现有Salesforce Object
→ 确认数据保存成功
→ MuleSoft更新Job状态
→ MuleSoft发布“任务状态事件”
→ LWC收到事件后重新查询Job和业务数据

优先复用现有Object。如果缺少字段，请列出最小必要字段，不要直接创建。

至少检查或建议：

- Status
- RequestKey

- ContextRecordId
- Progress
- AttemptCount
- ClaimedBy
- ClaimedAt
- LeaseUntil
- HeartbeatAt
- StartedAt
- CompletedAt
- ErrorCode
- ErrorMessage

建议状态：

QUEUED
→ CLAIMED
→ RUNNING
→ SAVING
→ COMPLETED

异常状态：

PARTIAL_FAILED
FAILED
CANCELLED
TIMEOUT

说明每个状态由Salesforce还是MuleSoft更新，以及允许的状态转换。

五、Platform Event设计

申请事件和完成事件必须分开，避免自触发循环。

例如：

AI_Job_Requested__e
- JobId
- RequestKey
- CorrelationId
- ContextRecordId

AI_Job_Status__e
- JobId
- Status
- Progress
- ErrorCode
- Message

要求：

1. 申请事件必须在Job事务提交后发布，即Publish After Commit。
2. MuleSoft必须通过Salesforce Pub/Sub Connector或现有标准连接器订阅。
3. MuleSoft不能收到事件后再次发布同一种事件。
4. 事件中不传递大量业务数据。
5. 事件可能重复投递，所以Salesforce和MuleSoft处理必须支持幂等。
6. 收到事件后必须根据Job Id重新读取Job状态。
7. 事件不是状态保存位置，Job Object才是可信状态。
8. 说明事件未收到、重复收到和延迟收到时的补偿方法。

六、LWC页面恢复要求

必须给出具体设计，保证以下场景正确：

1. 用户提交任务后留在当前页面。
2. 用户切换到其他Lightning页面后再返回。
3. 用户关闭浏览器后重新登录并打开页面。
4. 页面刷新。
5. LWC订阅事件前，任务已经完成。
6. LWC订阅暂时断线。
7. 同一用户存在多个历史Job。
8. 多个用户同时操作不同Job。

推荐初始化顺序：

1. 根据当前业务记录Id和当前用户查询最新相关Job。
2. 恢复Job状态和对应画面。
3. 订阅AI_Job_Status__e。
4. 订阅成功后再次查询Job，补偿“第一次查询与订阅之间”的时间差。
5. 收到与当前Job Id匹配的事件后重新查询Job。
6. Job为COMPLETED后查询现有业务Object并刷新画面。
7. disconnectedCallback中取消订阅和清除Timer。
8. 页面重新进入时不能只依赖JavaScript内存或localStorage，必须重新查询服务器上的Job。

可以保留30～60秒的低频轮询作为事件断线补偿，但不要固定永久5秒轮询。任务进入最终状态后立即停止轮询。

请明确说明：页面关闭期间LWC无法接收事件，因此重新打开时必须查询Job恢复状态。

七、MuleSoft处理要求

1. 收到申请事件后，根据Job Id查询Job。
2. 只有QUEUED或允许重试的状态才能处理。
3. 领取Job时防止多个Worker重复处理。
4. 使用RequestKey或CorrelationId保证AI调用和数据保存幂等。
5. 设置明确的maxConcurrency，不能无限并发调用AI。
6. 设置合理的AI Response Timeout，不能使用无限超时。
7. 重试必须有最大次数和退避时间。
8. AI返回429、5xx、连接中断和业务错误时分别处理。
9. AI调用已经被服务端接受但响应丢失时，不能直接重复收费调用；优先根据外部任务Id查询原任务状态。
10. Worker中断后，通过LeaseUntil和Heartbeat恢复Job。
11. 提供关闭Scheduler、暂停事件消费或把并发设为0的一键停止方式。
12. 监控QUEUED数量、最老Job等待时间、RUNNING时间、失败率和AI调用次数。

八、数据保存要求

MuleSoft负责把最终数据直接保存到现有Salesforce Object。

要求：

1. 不通过LWC或Apex传回大量结果。
2. 数据量较大时评估Salesforce Bulk API 2.0。
3. 使用External Id和Upsert避免重复保存。
4. 保存前将Job更新为SAVING。
5. 必须检查成功、失败和未处理记录。
6. 所有数据保存完成后才能把Job更新为COMPLETED。
7. 部分保存失败时使用PARTIAL_FAILED，不能标记COMPLETED。
8. 更新Job成功后再发布状态事件。
9. LWC收到完成通知后，只查询已保存的现有业务Object。
10. 说明Salesforce API配额、批大小和错误结果处理。
